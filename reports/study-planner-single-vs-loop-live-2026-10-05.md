# Study Planner 단독 모델 vs Loop 실측 QA 보고서

## 요약

같은 Study Planner 요구사항을 현재 패키지된 Loopline 앱에서 GPT-6-Astra Max 단독 Harness와 자동 모델 선택 Loop Harness로 각각 실행했습니다. 자동 완료 기준은 자동 반영, 프로젝트 검증, 브라우저 QA, 전체 작업 완료를 모두 충족하는 것으로 실행 전에 고정했습니다.

이번 1회씩의 측정에서는 **두 방식 모두 자동 완료에 실패**했습니다. 단독 실행은 계획 단계에서 끝났고, Loop는 4개 부분 작업 중 2개를 검증한 뒤 20회차 상한에 도달했습니다. Loop는 부분 코드와 테스트를 만들었지만 단독 실행보다 약 2.79배 오래 걸리고 11.45배 많은 토큰을 사용했습니다. 이 한 번의 실행만으로 모델 전반의 성공률을 단정할 수는 없지만, 이번 과제에서 Loop가 사람 개입 없이 끝까지 완성했다거나 토큰 효율이 높았다고 평가할 근거는 없습니다.

## 비교 조건

- 동일 프롬프트와 동일 소스 커밋 `337bd91477b14a28bf34acd41951093fae00e410`을 사용했습니다.
- 단독 실행은 계획·구현·판정을 GPT-6-Astra Max로 고정하고 대체 모델을 끄었습니다.
- Loop는 자동 모델 선택, 최대 20회차, 자동 검증, 자동 반영, 브라우저 QA 필수로 설정했습니다. MCP는 사용하지 않았습니다.
- 고정 비교 계약은 16개 브라우저 검사와 1440×900, 390×844 화면 크기로 실행 전에 기록했습니다.
- 실행별 런타임과 토큰은 Harness 기록을 사용했습니다. 실행 중 수동 중지·재개 횟수로 사람 개입을 계산했습니다.
- 금액 기준 실행별 과금액은 확인할 수 없어 달러 비용은 계산하지 않았습니다.

## 실패 지점과 자동 복구 결과

### 단독 Harness

총 7회 호출 중 계획 모델이 관찰 가능한 완료 기준을 포함하지 못한 응답을 두 번 냈습니다. 자동 형식 복구 뒤에도 계획 기준을 만들지 못해 부분 작업 계획 단계에서 종료됐습니다. 따라서 구현 파일, 프로젝트 테스트, 브라우저 QA는 생성·실행되지 않았습니다.

### Loop Harness

Loop는 다음 부분 작업을 만들고 진행했습니다.

- 데이터 상태와 저장 로직: 완료, 3회 시도
- 시맨틱 UI와 접근성 구조: 완료, 5회 시도
- 스타일과 반응형 레이아웃: 미완료, 12회 시도
- 전체 통합 QA와 실행 안내: 시작되지 않음

스타일 단계의 단위 테스트는 통과했지만 판정은 실제 화면 크기와 가로 넘침을 확인한 브라우저 근거를 요구했습니다. 그러나 실행은 그 근거를 QA 단계에서 생성하지 못한 채 같은 부분 작업을 반복했고, 20회차에서도 통합 QA에 도달하지 못했습니다. 종료 기록상 수동 개입은 없었지만, 자동 회차 연장도 막힌 단계를 해결하지 못했습니다.

## 사후 QA

실행 중 자동 완료 결과와 사후 확인 결과를 분리했습니다. 아래 항목은 Loop 실행이 끝난 다음 보존된 부분 작업 폴더에서 확인했습니다.

- **Loop 부분 프로젝트 내부 테스트: PASS 13/13.** 데이터 처리, 저장, 접근성 구조, 일부 스타일 규칙 테스트가 통과했습니다. 전체 통합 완료 증거는 아닙니다.
- **Loopline 앱 회귀 테스트: PASS 302/302.** `node --test tests/*.test.mjs` 실행 결과입니다.
- **실제 브라우저 스모크 검사:** 빈 화면, Enter 입력, 완료·되돌리기, 진행률, 필터, 제목·과목 검색, 새로고침 후 저장 유지, 삭제, 빈 입력 오류와 포커스 이동을 화면에서 확인했습니다.
- **발견된 기준 차이:** 과목 입력을 비워도 작업이 추가됩니다. 사전에 고정한 공통 브라우저 계약은 과목 입력 오류를 기대하므로 이 기준과 일치하지 않습니다.
- **제한:** 고정 16개 브라우저 계약은 양쪽 자동 실행에서 실행 기록이 없습니다. 사후 브라우저 검사는 좁은 인앱 브라우저 화면에서 진행했고, 1440×900 및 390×844 정확한 크기 측정은 하지 않았습니다. 단독 산출물이 없으므로 양쪽 결과에 동일한 화면 QA를 적용한 비교도 불가능했습니다.

Loop 부분 결과를 실제 화면에서 열어 둔 미리보기는 [Study Planner 미리보기](http://127.0.0.1:41901/)에서 확인할 수 있습니다. 테스트 입력은 삭제하고 빈 상태로 정리했습니다. 자동 완료가 아니라 미완성 작업의 사후 확인 화면입니다.

## 측정 준비량과 해석 한계

비교 실행에 앞서 잘못된 실행 환경을 감지해 취소한 설정 시도가 두 번 있었습니다. 이들은 비교 행에서 제외했지만 합계 **113,911토큰, 7회 호출**을 사용했습니다. 비교 실행과 설정 시도까지 모두 합치면 2,991,360토큰입니다. 앞으로 성능 실험에서는 패키지 앱의 브라우저 QA 브리지와 회차 설정을 본 실행 전에 검사해야 합니다.

이번 측정은 단일 과제·단일 실행씩의 결과입니다. 성공률, 모델의 보편적 성능, 작업 난이도별 우위로 일반화할 수 없습니다. 금액은 실행별 결제 데이터가 없어 보고하지 않았습니다.

## 개선 우선순위

1. **부분 작업 단위 브라우저 QA를 실행 가능하게 연결:** 스타일 단계가 요구하는 실제 레이아웃·가로 넘침 근거를 그 단계에서 만들어 판정에 전달해야 합니다.
2. **진전 없는 반복을 제한:** 코드나 검증 증거가 바뀌지 않은 상태로 거절이 반복되면 같은 구현을 계속 호출하지 말고 QA 복구 단계로 라우팅하거나 명확한 실패 원인과 재개점을 보존해야 합니다.
3. **회차와 토큰을 함께 제한:** 현재 회차 상한은 20회까지 사용해도 한 단계를 끝내지 못했습니다. 예산 기반 정지와 새 증거가 생길 때만 회차를 연장하도록 평가해야 합니다.
4. **공정한 재측정:** 두 방식 모두 실제로 프로젝트를 완성한 실행을 얻은 뒤에만 동일한 16개 브라우저 계약과 두 화면 크기로 최종 성공률을 비교해야 합니다.
