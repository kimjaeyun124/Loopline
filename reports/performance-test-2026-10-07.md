# Loopline 성능 실측 및 개선 보고서

## 요약

현재 코드의 Harness 실행 경로를 고정 응답 모의 제공자로 15회 측정하고, 앱 회귀 테스트 311개를 실행했습니다. 모의 환경에서 2회차 작업은 모든 조건에서 5/5회 검증·반영까지 완료됐습니다. 응답 지연이 0ms일 때 중앙 실행 시간은 1.237초, 응답마다 100ms를 넣었을 때는 2.162초였습니다. 응답 호출 9회에 넣은 대기 시간을 빼면 Harness와 로컬 검증 등을 포함한 나머지 시간은 중앙값 기준 약 1.24~1.26초였습니다.

이 수치는 **모델 품질이나 실제 API 성능을 나타내지 않습니다.** 제공자 서버가 현재 실행 중이 아니고, 고정된 모의 응답은 매 호출마다 15토큰으로 기록되도록 되어 있습니다. 따라서 오늘 실모델 토큰량·비용·완료율은 측정하지 않았습니다. 참고로 10월 5일의 더 큰 실제 Study Planner 비교에서는 GPT-6-Astra Max 단독과 Loop 모두 자동 완료에 실패했고, 당시 Loop는 더 긴 시간과 더 많은 토큰을 썼습니다. 이를 현재 버전의 실측으로 간주하지 않고 별도의 과거 기준으로 표시합니다.

가장 큰 개선 여지는 단순 호출 속도보다 **반복 실패를 빨리 감지하고, QA에 도달하기 전에 토큰을 소진하지 않도록 하는 것**입니다. 과거 실행에서는 Loop가 93회 호출과 2,646,326토큰을 쓰고도 20회차 한도까지 통합 QA를 마치지 못했습니다.

## 측정 범위와 조건

- 측정일: 2026-10-07
- 대상: 현재 로컬 저장소의 Harness 실행 경로
- 시나리오: 기존 `file.txt` 2회차 작업 fixture, 자동 검증·반영 포함
- 제공자: 결정적인 로컬 모의 제공자. 외부 AI API는 호출하지 않음
- 응답 지연: 제공자 응답당 0ms, 25ms, 100ms
- 반복 횟수: 조건별 5회, 총 15회
- 지표: 전체 경과 시간, 중앙값, 5회 표본 p95, 모의 제공자 호출 수, 완료·검증·반영 상태
- 회귀 테스트: `node --test tests/*.test.mjs`

## 로컬 Harness 성능

| 모의 응답 지연 | 중앙 실행 시간 | p95 | 중앙 제공자 호출 | 주입된 대기 시간 | 추정 Harness·로컬 처리 시간 | 완료·검증·반영 |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 0ms | 1.237초 | 1.543초 | 9회 | 0ms | 1.237초 | 5/5 |
| 25ms | 1.464초 | 1.553초 | 9회 | 225ms | 1.239초 | 5/5 |
| 100ms | 2.162초 | 2.381초 | 9회 | 900ms | 1.262초 | 5/5 |

추정 처리 시간은 전체 중앙값에서 `중앙 제공자 호출 수 × 모의 응답 지연`을 뺀 값입니다. Harness 내부 단계, fixture 서버 polling, 파일 작업, 검증·반영을 따로 계측한 값은 아니므로 각 요소의 비용으로 해석할 수 없습니다. p95는 조건별 표본이 5개뿐인 상황에서 계산한 값이며 이 표본에서는 최댓값과 같습니다. 안정적인 서비스 p95 추정치로 보기는 어렵습니다.

모든 실행의 모의 사용량은 135토큰(9회 × 응답당 고정 15토큰)으로 같았습니다. 이 값은 **실제 토큰 사용량이나 과금량이 아닙니다.** 5/5 완료 역시 fixture가 고정 성공 응답을 내도록 구성된 데 따른 결과라서 모델의 코드 품질이나 실제 과제 성공률을 보여주지 않습니다.

## 성능을 더 높이는 개선 방향

### 1. 진전 없는 반복을 차단하고 실패 원인에 맞게 복구

**우선순위: 최상**

현재 가장 큰 비용 위험은 수 초짜리 고정 Harness 처리보다 긴 실제 Loop에서 반복 호출이 누적되는 상황입니다. 부분 작업별로 직전 코드 변경, 검증 결과, QA 증거의 지문을 남기고, 같은 지문과 같은 실패 사유가 반복되면 동일한 구현 요청을 다시 보내지 않도록 해야 합니다. 한 번의 표적 복구 또는 역할 재배정 후에도 진전이 없으면 원인과 재개점을 보존해 안전하게 멈추는 편이 무제한 반복보다 완료율과 비용을 함께 지키기 쉽습니다.

### 2. 전체 토큰·시간 예산을 계획과 QA에 나눠 배정

**우선순위: 최상**

최대 회차 수만 제한하면 실패한 한 단계가 예산을 모두 소진할 수 있습니다. 과제 전체 토큰·시간 한도와 역할별 한도를 두고, 독립 QA와 마지막 수리 단계에 예산을 예약해야 합니다. 대체 모델은 단순 시간 초과만으로 매번 호출하지 말고, 새 오류 증거나 기존 모델의 한도 도달 같은 근거가 생겼을 때만 전환하면 중복 호출을 줄일 수 있습니다.

### 3. 구현 회차마다 독립 QA 증거를 생성

**우선순위: 높음**

과거 비교에서는 두 방식 모두 공통 브라우저 QA 실행 기록이 없었습니다. 웹 작업은 브라우저 검사에서 실제 입력, 저장, 반응형 크기, 키보드 동작을 확인하고 실패 요약만 다음 구현 회차에 전달해야 합니다. 검증되지 않은 추정 때문에 같은 UI 작업을 여러 번 다시 만드는 비용을 줄이고, 자동 완료 판정에도 실제 증거를 사용할 수 있습니다.

### 4. 반복되는 대화 문맥을 줄이고 체크포인트로 이어가기

**우선순위: 높음**

매 호출에서 전체 대화와 모든 이전 로그를 다시 보내기보다 요구사항, 현재 부분 작업, 마지막 변경, 실패한 검사와 필요한 파일만 담은 압축 컨텍스트를 유지하는 편이 토큰 비용을 낮출 수 있습니다. 이어하기 시에는 이미 검증된 부분 작업을 다시 계획·구현시키지 않고 보존된 체크포인트부터 시작해야 합니다.

### 5. 모바일 스트리밍 렌더링을 프레임 단위로 묶기

**우선순위: 중간, 추가 UI 계측 필요**

`native/LooplineNative/PhoneApp.tsx`의 스트리밍 수신 경로에서 텍스트 조각마다 상태 갱신이 발생하면 메시지 목록 렌더링이 자주 반복될 수 있습니다. 조각은 버퍼에 누적하고 화면 상태는 화면 주사율에 맞춰 묶어서 갱신하는 방안을 검토할 수 있습니다. 모델 목록이 큰 연결에서는 전체 목록을 한 번에 그리는 방식 대신 가상화 목록을 쓰는 것도 후보입니다. 이는 소스 확인으로 찾은 최적화 후보이며, 실제 프레임 저하나 개선 폭은 현재 보고서에서 측정하지 않았습니다. UI 반응성 계측 후 적용해야 합니다.

### 6. 병목을 분리 계측한 뒤 최적화

**우선순위: 중간**

모의 실행의 추정 로컬 처리 시간이 약 1.24~1.26초로 비교적 일정하지만, 이 값에는 polling·파일 작업·검증·반영이 합쳐져 있습니다. 다음 계측에서는 단계별 시작·종료 시간을 기록해 프로젝트 준비, 모델 요청, 파일 적용, 테스트, 브라우저 QA를 분리해야 합니다. 그 뒤 비용이 큰 단계에만 캐시·병렬화·불필요 작업 제거를 적용하면 안전하게 개선 효과를 비교할 수 있습니다.

## 한계와 미측정 항목

- 현재 Loopline API 서버가 실행되지 않아 오늘 실제 모델 제공자 호출을 할 수 없었습니다.
- 실제 모델별 품질, 비용, 토큰 사용량, 네트워크 지연은 미측정입니다.
- 결정적 fixture의 성공률은 실제 AI 성공률이 아닙니다.
- 모바일 화면 렌더링, 앱 시작 시간, 메모리 및 CPU 사용량은 계측하지 않았습니다. Instruments의 앱 시작 계측 시도가 제한 시간 후에도 정상 종료되지 않아 해당 수치는 보고에서 제외했습니다.
- 실행별 결제 금액 데이터가 없어 달러 비용은 산출하지 않았습니다.
