# 자동 모델 선택 Loop와 단독 모델 실측 비교

**측정일:** 2026-10-19 (Asia/Seoul)
**프로젝트:** Focus Ledger — 오프라인 할 일 관리 웹 앱
**목표:** Claude 우선 배정이 아닌 자동 역할 배정 결과를 확인하고, 같은 작업을 단독 모델로 제작해 완료·검증·토큰·시간을 비교한다.

## 요약

이번 과제의 단독 실행에서는 **GPT-6.1 Sol만 자동 완료와 반영을 통과**했습니다. Claude Sonnet 5는 계획을 만들었지만 구현 단계에서 Harness가 요구하는 JSON 작업 형식을 18회 연속 반환하지 못했습니다. Claude 실행은 39분 10초 동안 395,841토큰을 사용했고 파일을 하나도 만들지 못해 중단했습니다.

자동 Loop는 특정 모델을 고정하지 않고 역할별 모델을 선택했습니다. 계획 단계에는 토큰 효율 표본을 근거로 Claude Sonnet 5를 선택했고, 구현·판정에는 GPT-6.1 Sol을 주로 사용했습니다. 3회차까지 Node 테스트와 브라우저 QA는 통과했지만, 마지막 판정은 60,000자로 잘린 diff와 범위 밖 파일 저장 안전성 요구를 충분히 확인하지 못해 자동 완료를 거부했습니다.

이 과제에서 확인된 실용적 선택은 **GPT-6.1 Sol 단독 실행**입니다. 자동 모델 선택이 일반적으로 최선이라고 결론 내릴 근거는 아직 없습니다. 자동 선택은 Claude의 토큰 표본을 근거로 계획 역할을 배정했지만 Claude 구현 호출은 현재 Harness 작업 도구와 호환되지 않았습니다. 단독 GPT 실행만 최종 완료된 단일 표본이므로 이 결과를 모든 작업의 모델 순위로 일반화하지 않습니다.

## 비교 조건

### 단독 모델 기준선

- GPT-6.1 Sol과 Claude Sonnet 5에 같은 Focus Ledger 과제를 입력했습니다.
- 두 단독 실행은 Planner·구현·판정 역할을 모두 같은 모델로 고정하고, Effort는 high, 자동 대체 모델은 비활성화했습니다.
- 최대 3회차, 전체 1,200,000토큰, 준비 단계 300,000토큰의 동일 상한을 적용했습니다.
- 두 실행에 같은 범위 제한을 전달했습니다. 브라우저 데이터는 localStorage만 사용하고, 외부 의존성과 범위 밖 파일 저장은 추가하지 않도록 했습니다.
- Claude 실행은 구현 호출 16회를 모두 소진한 뒤 다음 회차에서도 같은 형식 오류가 반복되어 파일 변경이 없는 상태에서 정리했습니다. 단독 비교를 위해 다른 모델로 전환하지 않았습니다.

### 자동 Loop

- 과제 기능 범위와 최대 3회차는 같았지만 자동 Loop는 표준 2,000,000토큰·준비 500,000토큰 상한을 사용했습니다.
- 자동 Loop에는 단독 실행의 범위 제한 문구가 없었습니다. 따라서 자동 Loop와 GPT 단독 간 시간·토큰은 완전히 통제한 A/B 실험이 아닙니다.
- 각 실행의 독립 QA 계획은 모델이 따로 작성했습니다. 데스크톱·모바일의 대표 기능은 같지만 브라우저 assertion 수는 서로 다릅니다.
- 실행별 실제 달러 과금액을 확인하지 못해 비용은 계산하지 않았습니다. 토큰 수를 비용으로 환산하지 않았습니다.

### 공통 과제

Focus Ledger에 다음 기능을 요구했습니다: Enter로 공백 아닌 작업 추가, 완료·되돌리기·삭제, 상태 필터와 검색, localStorage 저장·복구, 접근 가능한 이름·키보드·포커스·상태 알림, 빈 상태, 1440×900 및 390×844 반응형, README와 오프라인 테스트.

## 자동 모델 선택이 실제로 한 일

자동 Loop의 계획 선택 판정은 완료 안정성·품질 우위를 가릴 표본이 부족하다고 기록했습니다. 대신 토큰 실측은 candidate_5가 4회 평균 97,590토큰, 기본 후보 candidate_0이 3회 평균 124,206토큰으로 candidate_5가 적다는 이유로 Claude Sonnet 5를 계획에 선택했습니다. 평균 호출 시간은 candidate_0이 253,128ms, candidate_5가 362,710ms로 더 짧았지만, 토큰 효율이 속도보다 우선이라 선택이 바뀌지 않았습니다.

| 역할 | 실제 모델 사용 | 보고 토큰 |
| --- | --- | ---: |
| 계획 | Claude Sonnet 5 4회, GPT-6 Sol 3회 | 163,260 |
| 구현 | GPT-6.1 Sol 7회 | 251,032 |
| 판정 | GPT-6.1 Sol 13회 | 508,186 |
| 전체 | Claude Sonnet 5 + GPT-6 Sol + GPT-6.1 Sol | 922,478 |

자동 Loop는 Claude 고정 실행은 아니었습니다. 다만 **완료 가능성의 근거가 부족한 상태에서 토큰 효율만으로 Claude를 계획 역할에 먼저 배정한 것**은 확인됐습니다. 이 선택은 품질 우위를 증명하지 않습니다.

## 확인된 문제와 해결 방향

### 1. 최선 모델을 증명하기 전에 토큰 효율로 역할을 선택함

자동 선택 결과 자체가 완료 안정성과 품질 우위를 판단할 표본이 부족하다고 밝혔습니다. 그런 상태에서 토큰 평균만으로 Claude를 계획 모델로 정했습니다. 토큰을 적게 쓰는 모델이 이 프로젝트를 더 정확하고 빠르게 완료한다는 근거는 없었습니다.

**해결 방향:** 완료·독립 QA 통과·사람의 복구 개입을 먼저 비교 가능한 성공 근거로 사용하고, 표본이 부족한 후보는 최선으로 표시하지 않습니다. 성공 근거가 비슷할 때만 토큰과 시간을 사용합니다. 모델별 Harness 도구 호출 성공률도 역할 배정 점수에 포함해야 합니다.

### 2. Claude 구현 응답이 JSON 작업 프로토콜과 호환되지 않음

Claude 단독은 18회 구현 시도에서 “모델 응답이 요청한 JSON 형식이 아닙니다”라는 오류를 냈습니다. 첫 회차의 16회 호출 한도를 다 쓴 뒤 다음 회차로 이어졌지만 파일은 만들어지지 않았습니다. 현재 구현 복구 흐름은 [harness-engine.mjs](../harness-engine.mjs#L2028) 및 [harness-engine.mjs](../harness-engine.mjs#L2040)에서 확인했습니다.

**해결 방향:** Claude 연결에 도구 호출·구조화 출력 지원을 맞추고, 응답 정규화와 실제 실패 응답 회귀 검사를 추가합니다. 형식 오류는 응답이 조금씩 달라도 연속 실패 횟수를 누적해 한 번 보정한 뒤 다음 저장 후보로 전환합니다. 단독 모델 벤치마크는 대체 없이 실패로 기록하되, 자동 Loop에서는 제한된 재시도 후 다른 모델이 이어받게 합니다.

### 3. 기능 검증 통과와 최종 완료 판정이 분리되어 있음

자동 Loop의 Node 20개와 브라우저 58개 검사는 각 회차에서 통과했지만, 마지막 판정은 전체 diff가 60,000자를 넘어 잘렸고 일부 파일·테스트 내용을 확인하지 못했다고 기록했습니다. 코드에서는 diff를 60,000자로 잘라 전달하고 길이를 넘으면 완료를 막습니다([harness-engine.mjs](../harness-engine.mjs#L1743), [harness-engine.mjs](../harness-engine.mjs#L1765)). 검증 성공이 최종 완료로 이어지지 못했습니다.

**해결 방향:** diff를 버리지 말고 파일 단위로 나눠 전부 검토한 뒤 요구사항·검증·브라우저 근거를 최종 판정에 전달합니다. 길이 제한에 걸리면 실패 처리 대신 페이지 방식의 검토를 이어갑니다. 요약만으로 판정하지 않도록 전체 변경 파일과 실행 가능한 테스트 근거를 보존해야 합니다.

### 4. localStorage 작업에 파일 시스템 저장 요구가 섞임

Focus Ledger는 브라우저 localStorage를 요구했지만 자동 Loop 판정은 별도 file-store.cjs, 원자적 파일 교체, 실패 경로 테스트까지 요구했습니다. 이 조건은 JSON과 저장 관련 단어의 근접 여부로 안내를 추가하는 [harness-engine.mjs](../harness-engine.mjs#L63)에서 시작해 최종 판정 검사에도 연결됩니다([harness-engine.mjs](../harness-engine.mjs#L2306)). 브라우저 저장소와 파일 시스템 저장은 다른 저장 방식입니다.

**해결 방향:** 파일 안전성 검사는 사용자가 파일 기반 저장을 요구하거나 실제 구현이 파일 시스템에 쓸 때만 적용합니다. localStorage·sessionStorage·IndexedDB만 사용하는 작업은 브라우저 저장으로 분류하고 파일 안전성 검사를 강제하지 않습니다. 실제 파일 저장 기능에는 원자적 교체 검사를 유지합니다.

### 5. 단독 모델 간 QA 계약이 완전히 같지는 않음

GPT 단독과 Claude 단독은 과제·역할 고정·Effort·예산을 맞췄지만 QA 계획은 각 모델이 따로 작성했습니다. 자동 Loop는 예산과 지침도 다릅니다. 브라우저 검사 수만으로 품질 순위를 매길 수 없습니다.

**해결 방향:** 다음 비교에서는 같은 고정 브라우저 QA 계약을 모든 모델 결과물에 적용합니다. 완료율·기능 QA·접근성·시각 회귀를 분리하고, 같은 프롬프트·지침·최대 시간·토큰으로 반복합니다.
