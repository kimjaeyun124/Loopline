# 웹사이트 제작 비교 재보고서: GPT-6 Luna Max 단독 Harness와 Loop Harness

작성일: 2026-10-01

## 요약

기존 Morrow와 Fieldnote 웹사이트 제작 결과를 다시 대조했습니다. 두 방식으로 만든 사이트는 각각의 동일한 독립 브라우저 QA를 모두 통과했습니다. 제작된 사이트의 핵심 기능 품질은 이번 두 사례에서 차이를 확인하지 못했습니다.

자동 완료는 프로젝트마다 달랐습니다. Morrow에서는 단독과 Loop 모두 최대 회차 안에 자동 판정·반영까지 끝내지 못했습니다. Fieldnote에서는 두 방식 모두 최종 실행이 검증과 자동 반영을 마쳤지만, Loop는 첫 시도에서 시간 초과 대체 모델 처리가 되지 않아 Harness를 수정하고 다시 실행해야 했습니다. 두 프로젝트만으로 성공률 우위를 주장할 수는 없습니다.

Loop는 두 비교 모두 더 오래 걸렸습니다. 기록된 토큰 합계는 Loop 쪽이 적지만, Fieldnote의 시간 초과 호출 사용량이 누락되어 있어 실제 절감량은 확정할 수 없습니다. 생성된 사이트 코드를 사람이 직접 고친 횟수는 최종 산출물 기준 양쪽 모두 0회였습니다. 다만 Loop는 첫 실패 복구를 위한 Harness 수정·재실행이 한 번 있었고, Morrow의 브라우저 검증은 Harness 바깥에서 별도로 해야 했습니다. 그 사람 공수는 분 단위로 측정하지 않았습니다.

이번에 별도로 확인한 Loopline 앱 QA는 전체 테스트 111/111 통과, ARM64 데스크톱 패키징 성공, 앱 재시작 후 연결 상태 표시까지 확인했습니다. 이는 Loopline 앱의 회귀·초기화 안정성 근거이며, 두 모델 방식의 웹사이트 품질 점수에는 합산하지 않았습니다.

## 비교 범위와 조건

- 비교 대상은 같은 종류의 웹사이트 제작에서 GPT-6 Luna Max 단독 Harness와 Loop Harness입니다.
- 프로젝트별로 양쪽 산출물에 같은 독립 검증 항목을 적용했습니다. Morrow는 7개, Fieldnote는 10개입니다.
- 실행 시간과 토큰 수는 기존 QA 보고서에 남은 값을 사용했습니다. 이번 턴에 새 웹사이트 생성 모델 호출을 반복하지 않았습니다.
- 각 프로젝트의 자체 테스트는 코드가 다르고 테스트 구성이 다르므로, 독립 공통 QA와 분리해서 봅니다.
- 사람의 개입은 앱 코드 수정, Harness 복구, 별도 브라우저 QA를 구분했습니다. 실제 사람의 소요 시간은 기존 기록에서 확인할 수 없습니다.

### 자동 완료 결과를 읽는 방법

- 프로젝트별 최종 설정 실행만 세면 자동 완료는 단독 1/2, Loop 1/2입니다. Morrow는 두 방식 모두 외부 브라우저에서 기능은 통과했지만 Harness 내부의 자동 완료·반영 단계가 끝나지 않았습니다.
- Loop의 Fieldnote 최초 시도는 대체 모델로 전환하지 못하고 실패했습니다. 수정 후 완료된 재실행까지 모든 시도를 포함하면 Loop는 1/3회 성공으로 기록됩니다. 이 값에는 제품 수정 전 실패와 수정 후 재실행이 함께 들어가므로 최종 설정 실행 1/2와 구분해야 합니다.
- 표본은 서로 다른 웹사이트 두 개뿐입니다. 50%나 1/3을 장기적인 성공 확률로 해석하지 않습니다.

## 사람의 개입과 완료 품질

| 항목 | GPT-6 Luna Max 단독 Harness | Loop Harness |
| --- | --- | --- |
| 최종 웹사이트 코드 직접 수정 | 두 프로젝트 모두 0회 | 최종 성공 산출물은 0회 |
| Harness 제품 수정·복구 | 확인되지 않음 | Fieldnote 첫 시도 실패 원인을 고친 뒤 재실행 1회 |
| 별도 브라우저 확인 | Morrow에서 자동 판정에 필요한 확인을 Harness 밖에서 수행 | Morrow에서 Chrome 샌드박스 제한으로 Harness 밖에서 별도 확인 |
| 사람 소요 시간 | 기록되지 않음 | 복구·확인 공수 기록되지 않음 |

독립 브라우저 기능 QA를 기준으로 보면 Morrow는 양쪽 7/7, Fieldnote는 양쪽 10/10입니다. 프로젝트별 공통 QA를 합산한 표시는 각각 17/17이지만, 이는 서로 다른 두 작업의 항목을 합친 값이지 하나의 통합 시험 점수는 아닙니다. 이 QA 범위에서는 어느 한 방식이 더 나은 최종 기능 결과를 냈다고 판단할 근거가 없습니다.

Loop가 보여준 차이는 여러 모델을 역할에 배치하고, 수정된 시간 초과 처리에서 우선순위 다음 모델로 넘긴 점입니다. 반대로 Morrow에서는 브라우저 검증이 샌드박스에서 막혀 자동 완료를 달성하지 못했고, Fieldnote에서는 초기 대체 처리 결함 때문에 제품 수선과 재실행이 필요했습니다. 사람 개입을 없애려면 모델 선택 자체보다 실패 후 복구, 브라우저 검증 결과 전달, 완료 판정의 연결을 더 안정화해야 합니다.

## 시간과 토큰

- 두 프로젝트의 최종 비교 실행 시간을 단순 합산하면 단독은 31분 57.494초, Loop는 68분 45.475초입니다. 이 사례들의 합산 기준으로 Loop가 약 2.15배 걸렸습니다. 서로 다른 과제를 합한 설명용 합계이며 일반 실행시간 예측은 아닙니다.
- 보고된 토큰을 단순 합산하면 단독은 1,060,832, Loop는 최소 905,043입니다. 표면상 기록량은 Loop가 최소 155,789개(약 14.7%) 적지만, Fieldnote에서 시간 초과된 Sol Max 호출의 사용량이 빠져 있습니다. Morrow와 Fieldnote의 기록 토큰도 제공자 청구 내역과 대조되지 않았으므로 실제 총량이나 비용 절감으로 단정하지 않습니다.
- 두 실행의 신뢰할 수 있는 달러 과금액은 확보되지 않아 비용은 비교하지 않았습니다.
- 결과적으로 이번 자료는 Loop가 토큰 효율적일 가능성은 보여주지만, 더 짧은 시간이나 더 적은 총 토큰으로 같은 품질을 냈다는 확정 증거는 아닙니다.

## Loopline 앱 자체의 최신 QA

이번에 해결한 초기화 문제를 반영한 Loopline 앱은 아래와 같이 확인했습니다.

- Loopline 회귀 테스트: `node --test tests/*.test.mjs` — **111/111 통과**
- 데스크톱 패키징: ARM64 패키지 생성 성공
- 앱 재시작 후 화면에서 Codex 1개와 API 연결 2개가 표시됨
- 앱 진입 경로, MCP UI 모듈 경로, 상태 확인 경로가 모두 HTTP 200으로 응답
- 새 모델 생성 요청이나 외부 유료 API 호출은 하지 않음

이 결과는 앱이 켜지고 연결 정보를 복원해 보여주는지 확인한 회귀 QA입니다. 실제로 Loop를 중단·재개하며 외부 모델 작업을 끝까지 수행한 비교 실험은 아닙니다. 따라서 위 웹사이트 생성 표의 성공률을 올리는 근거로 계산하지 않았습니다.

## 결론

현재 증거로는 최종 기능 품질과 사람의 사이트 코드 수정 횟수에서 두 방식의 차이가 확인되지 않았습니다. 자동 완료는 프로젝트별 최종 실행 기준 양쪽 1/2였고, Loop의 첫 Fieldnote 실패와 복구까지 세면 Loop는 1/3 시도에서 완료했습니다. Loop는 비교한 두 실행에서 더 오래 걸렸고, 토큰은 사용량이 빠진 호출 때문에 우위가 확정되지 않습니다.

Loop를 계속 쓰려면 모델 수를 늘리는 것보다 **검증을 자동으로 끝내는 경로**가 우선입니다. 다음 비교에서는 프로젝트 생성부터 독립 브라우저 검증, 판정, 자동 반영까지 같은 기준으로 다시 실행하고, 시간 초과 호출의 토큰 사용량과 사람의 실제 개입 시간을 빠짐없이 기록해야 합니다. 그래야 사람 개입 감소와 최종 완료율 개선을 판단할 수 있습니다.
